## Upgrade notes

Operators moving from **v0.1.0** → **v0.2.0** (same bundle/bootstrap flow; pin image tag `v0.2.0`).

### 1. Knowledge base (Docling-only parsing, #77)

- New uploads and re-parses use **Docling** as the default parser; legacy parser paths are removed from the default pipeline.
- **Before cutover:** plan re-parse for collections that still depend on old parser output or broken chunks.
- **After upgrade:** spot-check search/RAG on critical documents; trigger **re-parse** from the portal where results look stale.
- Local/dev: Docling optional in `infra.yml`; production VM stacks include docling-serve where your compose profile expects it.

### 2. Vector / RAG (Chroma, #93)

**v0.1.0** stored Chroma in a Docker named volume (`chroma_data` → `/chroma/chroma`). **v0.2.0** persists under the host data root: `${DATA_ROOT_HOST_PATH}/chroma` mounted at `/data`.

Pick one:

1. **Move existing data (keep embeddings)** — before or during upgrade, copy Chroma files from the old volume into `${DATA_ROOT_HOST_PATH}/chroma/` (create the directory — `host-deploy` / bootstrap does this on v0.2.0). Example after stopping the stack: locate the old volume (`docker volume inspect <project>_chroma_data`), copy its contents into the new folder, then deploy `v0.2.0`.
2. **Re-sync (simpler, slower)** — start with an empty `${DATA_ROOT_HOST_PATH}/chroma/`, deploy `v0.2.0`, then rebuild vectors from Postgres via `scripts/vector_sync_cli.py sync` (per tenant / source). Use when you have no usable Chroma backup.

No in-app Chroma “migration” job — either **copy host data** or **re-sync**.

### 3. Sandbox egress (new `egress-proxy` image, #76)

- Release ships **`egress-proxy`** alongside sandbox controller/runner; runners should use `HTTP_PROXY` to Squid.
- **Allowlist:** platform defaults are in the image; tenant-specific domains go in `${DATA_ROOT_HOST_PATH}/egress/domains.custom.txt`, then run `deploy/scripts/egress-proxy-reload.sh` after edits.
- After upgrade, run a sandbox smoke test that needs outbound HTTP; add missing domains to the custom file if calls fail.

### 4. LLM registry (#87)

- Model profiles may apply **default reasoning effort** where supported.
- **After upgrade:** open tenant **LLM settings**, confirm provider credentials and each active model; run one agent turn that uses extended reasoning if you rely on it.

### 5. Runtime / SSO (no mandatory migration)

- **SSO (#83):** safe to retry pending email attach — no data migration.
- **Scheduled tasks (#86):** JWT encoding uses `python-jose`; no action if tasks already run on v0.1.0.
- **LangGraph checkpointer (#71):** survives PostgreSQL restarts better; no schema step beyond normal app migrations (`migrate` / release bundle).

### Suggested upgrade order

1. Backup Postgres; copy old `chroma_data` volume data into `${DATA_ROOT_HOST_PATH}/chroma/` **or** plan a vector re-sync (see §2).
2. Deploy images at `v0.2.0` (bootstrap or compose pull).
3. Run DB migrations if your bundle release includes new revisions.
4. Verify LLM settings, one KB search, one sandbox job, one Slack channel thread if used.
